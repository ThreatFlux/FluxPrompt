# Threat Model

This threat model defines what FluxPrompt analyzes, what it can reasonably signal, and what remains the host application's responsibility. It applies to the current `0.2.x` implementation.

## Security Objective

FluxPrompt's objective is to give a Rust application local, explainable signals that a text string resembles known prompt-injection or manipulation patterns. The application can use those signals when deciding whether to reject, quarantine, transform, review, or forward the text.

FluxPrompt is not intended to prove that input is safe or malicious. It is one control in a layered system.

## Assets at Risk

Depending on the host application, an injection can threaten:

- system prompts and hidden application instructions;
- private conversation, retrieval, tenant, or model context;
- credentials and data reachable through tools;
- integrity of tool arguments and external actions;
- application policy, audit data, availability, and user trust.

The host application must identify its actual assets and consequences. FluxPrompt has no knowledge of permissions, tenant boundaries, business impact, or downstream tool semantics.

## Adversaries and Sources

Assume an attacker can submit or influence text that reaches an LLM, including:

- direct user prompts;
- documents, web pages, email, tickets, code, and database fields used for retrieval;
- tool results and third-party API responses;
- text generated by another model;
- encoded, obfuscated, fragmented, or multilingual content;
- a sequence of individually benign-looking messages.

An attacker may know FluxPrompt's source code and tune input against its rules. Security must not depend on patterns or thresholds remaining secret.

## Trust Boundary

The library boundary is one call:

```text
untrusted or mixed-trust text -> FluxPrompt::analyze -> advisory result
```

FluxPrompt receives only a `&str`. It is not told which bytes came from a system message, a user, retrieval, or a trusted developer. If an application concatenates trusted and untrusted content, the detector cannot recover those boundaries.

The returned `PromptAnalysis`, including any `mitigated_prompt`, remains untrusted data. The caller decides what happens next.

## In-Scope Signals

The current implementation attempts to signal:

- direct instruction-override and jailbreak language;
- role impersonation and context-boundary manipulation phrases;
- system-prompt and data-extraction requests;
- selected social-engineering, authority, urgency, and trust phrases;
- selected encoding and obfuscation shapes;
- unusual entropy, repetition, punctuation, capitalization, and formatting;
- combinations of several detected threat types.

Custom regexes can add application-specific signals. A caller can analyze retrieved content or model output explicitly, but FluxPrompt does not discover or intercept those channels itself.

## Non-Goals and Limitations

FluxPrompt does not provide:

- guaranteed detection, prevention, or a complete prompt-injection taxonomy;
- semantic understanding, embeddings, or model-based classification;
- reliable multilingual or Unicode-confusable coverage;
- conversation-level or cross-request reasoning;
- provenance or trust-label tracking within mixed content;
- automatic inspection of images, audio, files, tool calls, tool outputs, or retrieved documents;
- authorization, capability control, policy evaluation, sandboxing, rate limiting, or network isolation;
- secret redaction or data-loss prevention;
- validation that a sanitized prompt is safe or meaning-preserving;
- regulatory compliance or a substitute for a security review.

Adaptive attackers can evade deterministic rules. Benign prompts—especially security research, code, role-play, encoded data, and quoted attacks—can be flagged.

## Important Failure Modes

| Failure mode | Consequence | Required host control |
| --- | --- | --- |
| False negative | Harmful text reaches the model or tools | Least-privilege tools, authorization, isolation, output/tool validation, monitoring |
| False positive | Host policy may reject or transform legitimate work | Calibration, human review, user-safe retry path, decision telemetry |
| Misused mitigation text | Caller forwards original input or treats a warning as enforcement | Explicit branch on the result before any downstream request |
| Lossy sanitization | Meaning changes or an attack survives transformation | Treat sanitized text as untrusted; revalidate and constrain downstream actions |
| Configuration drift | Thresholds or custom rules change without review | Version configuration, validate in CI, audit deployment changes |
| Resource abuse | Large or concurrent requests consume host resources | Enforce body, concurrency, CPU, memory, and rate limits outside FluxPrompt |
| Sensitive telemetry | Prompts or attack content leak through logs | Log decisions/IDs by default; restrict and expire any captured content |
| Rule disclosure | Attackers tune inputs around known patterns | Assume source and configuration are known; rely on layered controls |

## Response-Strategy Boundary

`ResponseStrategy` selects a returned string for flagged input. Even `Block` does not block a socket, cancel a request, or remove the original string from application memory. A correct integration must stop the downstream path itself:

```rust
use fluxprompt::{FluxPrompt, RiskLevel};

async fn enforce(
    detector: &FluxPrompt,
    untrusted_text: &str,
) -> Result<(), Box<dyn std::error::Error>> {
    let analysis = detector.analyze(untrusted_text).await?;

    if analysis.is_injection_detected() {
        audit_decision(analysis.risk_level());
        return Err("request rejected by prompt policy".into());
    }

    invoke_agent(untrusted_text).await
}

fn audit_decision(_: RiskLevel) {}

async fn invoke_agent(_: &str) -> Result<(), Box<dyn std::error::Error>> {
    Ok(())
}
```

## Recommended Defense in Depth

Use FluxPrompt alongside controls that do not depend on detecting attacker wording:

1. Keep system instructions and untrusted data structurally separate.
2. Give the model and each tool the least privilege required for the current task.
3. Authorize tool actions using trusted application state, not model assertions.
4. Validate tool names, arguments, destinations, and output schemas.
5. Require confirmation or review for irreversible or high-impact actions.
6. Isolate code execution and network/file-system access.
7. Classify and filter retrieval sources before adding them to context.
8. Apply output validation and data-egress controls.
9. Enforce service-level request size, concurrency, timeout, and rate limits.
10. Monitor decisions and downstream actions without retaining unnecessary prompt content.
11. Maintain application-specific adversarial regression tests.

## Assumptions

The guidance assumes:

- the host checks and enforces the returned decision before invoking downstream components;
- configuration and binaries are protected from unauthorized modification;
- the host limits untrusted input before expensive processing;
- operators test thresholds against their own distribution;
- bypasses and crashes are handled as security-relevant defects when they weaken a deployed control.

If these assumptions do not hold, FluxPrompt should be treated only as telemetry.

## Reporting Bypasses

A reproducible bypass, denial of service, unsafe transformation, parser/truncation issue, or configuration behavior that contradicts this model may be security-relevant. Do not publish working exploit details before maintainers can triage them. Follow [SECURITY.md](../SECURITY.md) and include the library commit, configuration, input, observed result, expected result, and impact.

## Review Triggers

Update this threat model when the project adds or changes:

- a detector or scoring mechanism;
- model, embedding, network, file, or tool integration;
- conversation or provenance tracking;
- mitigation semantics;
- configuration enforcement;
- metrics or prompt retention;
- a trust boundary or supported deployment pattern.
